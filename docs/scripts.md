### `db:seed` — المدخل الموحّد وخطواته

`seed.ts` **منسّق (orchestrator) فقط**: يقرأ الـflags، يرتّب الخطوات، ويملك وحده فتح/إغلاق الـpool. كل خطوة موديول مستقل يصدّر دالة async عادية ولا يلمس الاتصال.

> **وهو كذلك composition root ثانٍ** — يستدعي `configureAuth(...)` قبل أي خطوة، بنفس أسطر `src/app.ts`. الخطوات تمرّ بالـservices الحقيقية، وتلك تحلّ `accountStore`/`authProvider`/`emailSender` من منافذ فارغة حتى يوصلها أحد؛ ولم يكن أحد يوصلها، فكان `--demo` يموت عند أول تسجيل ذاتي (`registerStaff` يُصدر رمز تحقق ثم يُسجّل الدخول — والثلاثة على ذلك المسار). ظهر العطل كخطأ `EmailSender has not been configured` فقط لأن منفذ البريد يرمي أولاً.
>
> **والناقل هنا مُتجاوَز عمداً**: `emailSender` يُمرَّر ستَباً يُرجع `no_transport`، فلا يذهب أي ظرف عنوانه `@qirtas.test` إلى `SMTP_HOST` الحقيقي مع كل `db:setup`، ولا يُكتب `auth.email.verification_sent` برسالة لم تُبنَ. الأثر: صف `auth.email.verification_send_failed` لكل حساب من مسار الانتظار، يحذفه `--reset` مع بقية سجلّ المستخدم التجريبي.

| Flag | الخطوة | الملف | ملاحظات |
| ---- | ------ | ----- | ------- |
| _(دائماً)_ | كتالوج الصلاحيات + كتالوج الأدوار + أسماء الصلاحيات المعروضة (ar/en) | `seed-core.ts` | آمن لإعادة التشغيل (upsert بالمفتاح الطبيعي: مفتاح الصلاحية / اسم الدور / `(language_code, key)`) |
| `--admin` | إنشاء أول حساب Super Admin | `bootstrap-super-admin.ts` | نفس الـservice ونفس الـzod schema المستخدمَين في `POST /users/bootstrap-super-admin`. يتخطّى بصمت لو جدول `users` غير فارغ. البيانات من `SEED_ADMIN_*` (افتراضي: `super_admin@admin.com` / `P@ssw0rd@123`) |
| `--demo` | بيانات عربية تجريبية (15 فرع، 67 مستخدم على كل الأدوار وكل الحالات) عبر service layer الحقيقي | `seed-demo-arabic-data.ts` | **نقطة البداية الدائمة لأي جولة تجربة/تطوير**. يتطلّب Super Admin موجوداً (استخدم `--admin` معه أو قبله) |
| `--reset` | حذف فعلي لكل صفوف الديمو قبل إعادة الزرع | ↑ نفسه | لا يعمل إلا مع `--demo` (خطأ صريح لو انفرد). hard delete — استثناء موثّق داخل الملف من قاعدة "لا Hard Delete"، محصور بـ`@qirtas.test` والفروع التجريبية بالاسم |
| `--fr` | اللغة الفرنسية الديناميكية | `seed-french-ui-translations.ts` | ملف "عدّل ثم أعد التشغيل" — تُحرَّر النصوص فيه يدوياً |
| `--ui-overrides-demo` | demo آلية override لنص UI من الخادم | `seed-ui-text-overrides-demo.ts` | **يغيّر نصاً ظاهراً عمداً** (`welcomeBack`) — مستثنى من `--all` بقصد |
| `--all` | = `--admin --demo --fr` | — | بدون `--ui-overrides-demo` وبدون `--reset` |
| `--help` | يطبع الاستخدام كاملاً ويخرج | — | أي flag غير معروف → خطأ صريح، لا تجاهل صامت |

> **أسماء الصلاحيات المعروضة داخل `seed-core.ts` لا في ملف منفصل**: كل عنصر في `PERMISSIONS` يحمل `display: { ar, en }` الخاص به. كان لها سابقاً سكربت مستقل (`seed-permission-translations.ts`) بقائمة مفاتيح موازية تُزامَن يدوياً — أُلغي، ومعه خطر إضافة صلاحية بلا ترجمة. راجع [../../docs/reference/dynamic_localization.md](../../docs/reference/dynamic_localization.md) §13.

## قاعدة البيانات عبر Docker (الطريقة الموصى بها محلياً)

`docker-compose.yml` بالجذر يشغّل PostgreSQL 16 بنفس بيانات `DATABASE_URL` الافتراضية بـ`.env.example` (`postgres`/`postgres`/`qirtas_dev` على `5432`) — بدون أي تعديل إضافي.

| Script/Command           | ماذا يسوي                                                        |
| ------------------------ | ---------------------------------------------------------------- |
| `docker compose up -d`   | يشغّل حاوية PostgreSQL بالخلفية (أول مرة يسحب الـimage تلقائياً) |
| `docker compose ps`      | حالة الحاوية (`healthy` يعني جاهزة لقبول اتصالات)                |
| `docker compose down`    | يوقف الحاوية (البيانات تبقى بـvolume `postgres_data`)            |
| `docker compose down -v` | يوقف الحاوية **ويحذف** البيانات نهائياً (تصفير كامل)             |
| `docker compose logs -f` | متابعة لوج القاعدة مباشرة                                        |

## إعداد أول مرة (Setup) — ✅ مُختبر فعلياً ضد قاعدة حقيقية (2026-08-02)

1. `npm install`
2. `.env` جاهز افتراضياً بنفس قيم `docker-compose.yml` — لا حاجة لتعديل لو مستخدم Docker محلياً.
3. `docker compose up -d` — شغّل القاعدة (تحقق بـ`docker compose ps` أن الحالة `healthy`).
4. `npm run db:setup` — أمر واحد: ينشئ كل جداول الـidentity module، يزرع الأدوار والصلاحيات وأسماء الصلاحيات، ينشئ أول Super Admin، ويزرع البيانات التجريبية.
5. `npm run dev` — يشغّل السيرفر على `http://localhost:3000` (أو `PORT` بالـ`.env`).
6. تحقق: `curl http://localhost:3000/health` يرجع `{"status":true,...}`.
7. سجّل دخول بـ`super_admin@admin.com` / `P@ssw0rd@123` (أو قيم `SEED_ADMIN_*` اللي ضبطتها قبل الخطوة 4).

> إنشاء الـSuper Admin عبر HTTP (`POST /api/v1/users/bootstrap-super-admin`) ما زال يعمل كبديل يدوي — نفس الـservice ونفس الـschema بالضبط، وينجح فقط لو عدد اليوزرز = صفر.

> ✅ **تم التحقق الكامل فعلياً (2026-08-02، بعد توحيد السيدات)**: `db:setup` من قاعدة فارغة (migrate → 26 صلاحية + 10 أدوار + 52 صف `permission.*` → Super Admin id 1 → 15 فرع + 67 مستخدم) → `db:seed -- --fr` (55 مفتاح) → إعادة تشغيل `db:seed -- --admin --demo` بدون `--reset` (تخطّى الـadmin وكل الـ67 مستخدم — idempotent) → `--reset` منفرداً و flag غير معروف كلاهما يفشل برسالة استخدام واضحة. كله ضد PostgreSQL حقيقي داخل Docker.

## `npm run check:messages` — لا رفض بلا ترجمة

فحص ساكن (بلا خادم): كل `BusinessError`/`ForbiddenError`/`UnauthorizedError`/`RateLimitError` يجب أن يمرّر `messageKey` مسجَّلاً بـ`core/i18n/messages.ts`.

**لماذا**: وسيط `message` هو **النص الإنجليزي الاحتياطي**. فبلا مفتاح، `resolveMessage` لا تجد ما تبحث عنه وتُرجعه كما هو — فيقرأ أدمنٌ عربيٌّ جملةً إنجليزية وسط مهمته. لا شيء يفشل، ولا شيء يُسجَّل، والطريق الوحيد للاكتشاف هو الاصطدام بذلك الرفض بالذات والنظر للشاشة.

**وهكذا بقي مخفياً**: بلاغ حيّ (2026-08-05) عن «This role has active user assignments…» بشاشة عربية قاد لتدقيق كشف **٢٧ رمية بلا مفتاح**. والقاعدة كانت مكتوبة بـ`qirtas_app/readme/rest_api.md` §6.1 منذ بناء نظام الرسائل — **وقاعدة مكتوبة بلا فحص مجرّد اقتراح**.

**النطاق**: الأصناف الأربعة التي تصل نصّها للمستخدم حرفياً **وتقبل** `messageKey`. أما `Error` العادي (خطأ مبرمج أو إيقاف سكربت) و`NotFoundError`/`ValidationError` (بنيويان، والعميل يرسم نصّه) فخارج النطاق **قصداً لا سهواً**، وموثَّق سبب كلٍّ بالملف.

> **تحقق من أن الفحص يفحص**: حُذف مفتاح واحد عمداً → فشل الفحص وسمّى الملف والسطر والرسالة؛ ثم أُعيد → ✅.

## `npm run smoke` — اختبار دخان للعقد

```bash
npm run dev      # طرفية أولى
npm run smoke    # طرفية ثانية
```

يُشغَّل مقابل خادم حيّ ويؤكّد **ثوابت العقد** لا نتائج العمل. ٢٤ فحصاً، أقل من نصف ثانية، ويعيد exit code 1 عند أي فشل.

**لماذا وُجد**: كل عطل بُني هذا السكربت لصيده كان غير مرئي للمراجعة وللـtype checker، **لأن أياً منها لم يفشل**. كلها أعادت جواباً معقولاً حسن الشكل وخاطئاً:

- `?is_active=false` أرجع كل الأدوار الفعّالة (`Boolean('false') === true`) — بخمسة فلاتر معاً
- `deactivate` بلا نظير، فالدور المتقاعد لا يعود أبداً — ولا شيء يخطئ
- `level: null` (بلا سلطة) وصل فخُزِّن `0` (أعلى سلطة موجودة)

القاسم المشترك: نظام لا يميّز «غائب» عن «فشل». الـtype checker لا يراه، والمراجع القارئ للـdiff لا يراه — **لكن عددين يجب أن يختلفا، مقارنَين ببعضهما، يريانه**.

| القاعدة عند الإضافة | لماذا |
|---|---|
| قراءة فقط افتراضاً | الكتلة المُطفِرة الوحيدة تُنشئ دوراً مؤقتاً وتحذفه بـ`finally` — اختبار يخلّف نفايات يتوقف الناس عن تشغيله |
| تأكيد **علاقات** لا أعداد مطلقة | `active + inactive === all` ينجو من إعادة زرع؛ `total === 11` لا. واختبار لا يُوثَق به لا يُشغَّل |
| كل فحص يُسمّي ما ينكسر عند فشله | سطر أحمر بلا تفسير يُعاد تشغيله حتى ينجح |

> **تحقق من أن الاختبار يصطاد فعلاً (2026-08-05)**: أُعيد `z.coerce.boolean()` إلى `roles.is_active` عمداً → **٤ فحوص فشلت** (بينها «الدور المعطَّل قابل للإيجاد» كأثر تابع) وexit code 1. ثم أُعيد الإصلاح → ٢٤/٢٤. اختبار لم يفشل قط لا يُثبت شيئاً.

## `npm run test:import` — تطابق التطبيعَين بطرفَي كشف التكرار

`flagDatabaseDuplicates` تقارن مفتاحاً تُطبّعه **JavaScript** (`duplicateKey`: قصّ · تصغير · طيّ المسافات) بمفتاح تُطبّعه **SQL**. تطبيعان بلغتين، ونصٌّ واحد يجب أن يخرج متطابقاً — ولا شيء يفشل حين ينحرفان.

**والانحراف لا يبدو خطأً**: الاستعلام يعمل، ويُرجع صفوفاً، ويطابق كل اسم تهجئته قياسية أصلاً — أي معظم الأسماء. الاسم الوحيد الذي يسقط هو ما اضطرّ المحرّك **لتغييره** (مسافة مزدوجة، تاب، فراغ ذيلي)، فيُبلَّغ عنه كجديد: **شاشة المراجعة تعرض صفراً من الأخطاء**، والمستخدم يؤكّد استيراداً قيل له إنه نظيف، فتموت الكتابة عند الفهرس الفريد — بعد أن يكون رمز التخزين المؤقت (single-use) قد استُهلك.

**البلاغ الحيّ (2026-08-13)**: `'\s+'` مكتوبة داخل template literal، فتبتلع JavaScript الشرطة المائلة ويصل Postgres النمط `'s+'` — أي **حرف s**. الفرع «فرع  مركز» (مسافتان) عبر الفحص بلا أي خطأ، ثم ردّ الخادم 500، ثم أعاد عميلُ الفلاتر المحاولة على رمز مُستهلَك فقرأ المستخدم «هذه العملية استُخدمت أو انتهت مهلتها» عن ملف رفعه للتوّ.

| الفحص | ونقيضه معاً |
|---|---|
| الاسم بمسافة مزدوجة يُكتشف | لأن دالةً تُرجع «الكل موجود» تنجح فيه — فيُثبَّت معه أن **اسماً جديداً لا يُطابَق** وأن الملف الجديد يحصل على رمز وصفٍّ صالح |
| الاسم بتهجئة قياسية يُكتشف | **وهو الفحص الذي بقي أخضر طوال فترة العطل** — سويةٌ لا تحويه كانت ستشحن هذه العلّة |

> **تحقق من أن الاختبار يصطاد**: أُعيدت `'\s+'` عمداً → فشل فحصان (المسافة المزدوجة وحدها)، والخمسة الباقية خضراء — وهذا بالضبط شكل العطل الأصلي. ثم أُعيد الإصلاح → ٧/٧.

قراءة فقط عدا فرعَين يُنشآن ويُحذفان بـ`finally` (القاعدة الواردة أعلاه).
